# 文件上传与下载录屏讲解稿

建议总时长 9 分钟，上传和下载各留一点操作时间。

## 一、开始前准备

1. 启动 MySQL、Redis 和 SeaweedFS。
2. 启动后端 `ContestApplication`。
3. 准备一个小文件批量上传页面：
   `http://localhost:8080/file-test.html`
4. 准备一个大文件分片上传页面：
   `http://localhost:8080/file-upload.html`
5. 准备一个 10 MB 左右的大文件。

## 二、录屏顺序

### 0:00-0:40 架构说明

展示结构：

```text
浏览器
  → FileController / UploadController
  → FileService / UploadService
  → StorageService
  → LocalStorage 或 SeaweedStorage
  → SeaweedFS / 本地磁盘
```

说明业务层只依赖 `StorageService` 接口，因此本地磁盘和 SeaweedFS 可以通过配置切换。

### 0:40-1:40 小文件批量上传

打开 `file-test.html`：

1. 一次选择 3 至 5 个文件。
2. 点击批量上传。
3. 展示每个文件独立的成功或失败结果。

代码讲解：

- 前端将多个文件放入同一个 `FormData`；
- 后端 `/api/v1/files/batch` 接收文件列表；
- 后端逐个计算 SHA-256、保存文件和写入数据库；
- 单个文件失败不会导致整批回滚。

### 1:40-4:10 大文件分片、合并与坏片重传

打开 `file-upload.html`：

1. 选择大文件，分片大小选 `1 MB`。
2. 勾选“模拟第 2 片损坏一次”。
3. 开始上传。
4. 展示日志中的错误哈希、服务端 `422`、坏片编号和自动重传。

代码讲解：

- 总片数使用文件大小除以分片大小并向上取整；
- 前端用 `file.slice(start, end)` 截取分片；
- 前端计算分片 SHA-256，并放入 `X-Chunk-SHA256` 请求头；
- 后端重新计算分片摘要，不一致时返回 `invalidChunks`；
- `file_chunk` 保存分片序号、路径、大小和 SHA-256；
- 合并前逐个读取分片复核哈希；
- 发现损坏或缺失时返回 `retryChunks`；
- 前端只重传这些编号，不需要从头上传；
- 合并后服务端再核对完整文件 SHA-256。

### 4:10-5:20 上传断点续传

1. 上传过程中点击“暂停”。
2. 刷新页面。
3. 页面显示 `uploadId` 和已经上传的分片数。
4. 重新选择同一个文件。
5. 点击“刷新后续传”。

代码讲解：

- 浏览器在 `localStorage` 保存任务编号、文件名、大小和摘要；
- 后端 `progress` 接口返回已经上传的分片序号；
- 前端跳过这些分片，只上传缺失部分。

### 5:20-7:10 下载进度与下载断点续传

分片合并完成后：

1. 点击“开始 / 继续下载”。
2. 展示下载进度条按字节增长。
3. 中途点击“暂停下载”。
4. 再点击“开始 / 继续下载”。

代码讲解：

- 前端每次发送 1 MB 的 Range 请求；
- 下载位置保存在已经接收的字节数中；
- 继续下载时发送：

```http
Range: bytes=已下载字节数-
```

- 后端返回 `206 Partial Content`；
- `Content-Range` 告诉客户端当前区间和文件总大小；
- 越界范围返回 `416`。

### 7:10-8:20 高并发下载

点击“三路并发下载测试”：

1. 同时发起 3 个 Range 请求；
2. 三条结果都显示 `HTTP 206`；
3. 三个请求分别返回对应字节区间。

讲解重点：

- 每次下载请求相互独立，不使用共享文件锁；
- 文件保存在 SeaweedFS 中，多路读取不会争抢同一个本地文件；
- Tomcat 使用多线程处理请求；
- Range 请求只读取指定区间，避免每次读取整个文件。

### 8:20-9:00 总结

总结四点：

1. 分片机制支持大文件上传；
2. SHA-256 校验能定位损坏分片并只重传坏片；
3. `uploadId` 和 HTTP Range 分别支持上传、下载断点续传；
4. 存储层通过 `StorageService` 抽象，可在本地磁盘和 SeaweedFS 之间切换。
